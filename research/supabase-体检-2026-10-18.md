## S1 信任边界无法自证

`schema.sql` 是整套安全模型的唯一依据，但它在线上是否真的执行过、执行的是哪个版本、有没有人手工改过策略，仓库里没有任何证据。管理员面板的“schema 健康检查”只试读四张表，见 `auth.py:497-506` 与 `auth.py:681-689`。它能发现“表没建”，发现不了“RLS 被关掉”“函数执行权被重新授给 anon”“策略被改名”。

邀请码门禁还依赖 Supabase Auth 控制台里的“允许新用户注册”开关。`auth.py:8-9` 的注释说已经关闭，但这个开关不在代码里，无法从仓库验证。如果它是开着的，任何人拿公开的 anon key 调 `/auth/v1/signup` 就能绕过邀请码建号。

建议加一个只对 `service_role` 开放的自检 RPC，把 `pg_class.relrowsecurity`、`pg_policies`、`has_function_privilege`、关键列默认值、`auth` 配置中可读的部分汇总成 jsonb，管理员面板每次解锁时比对期望值，不一致就直接报错并停止管理操作。自检 SQL 放进 `supabase/` 与迁移脚本一起管理。

```sql
create or replace function public.security_selfcheck()
returns jsonb
language sql
security definer
set search_path = public
as $$
    select jsonb_build_object(
        'rls', (
            select jsonb_object_agg(c.relname, c.relrowsecurity)
            from pg_class c
            join pg_namespace n on n.oid = c.relnamespace
            where n.nspname = 'public' and c.relkind = 'r'
        ),
        'policies', (
            select jsonb_agg(jsonb_build_object(
                'table', tablename, 'name', policyname, 'cmd', cmd))
            from pg_policies where schemaname = 'public'
        ),
        'grants', (
            select jsonb_agg(jsonb_build_object(
                'fn', p.proname,
                'anon', has_function_privilege('anon', p.oid, 'execute'),
                'auth', has_function_privilege('authenticated', p.oid, 'execute')))
            from pg_proc p
            join pg_namespace n on n.oid = p.pronamespace
            where n.nspname = 'public'
        )
    );
$$;

revoke execute on function public.security_selfcheck() from public;
grant execute on function public.security_selfcheck() to service_role;
```

验收标准：故意在测试库上 `alter table public.datasets disable row level security`，自检必须返回告警，管理员面板必须拒绝继续操作。

控制台需要人工确认的清单放在文末。

## S2 GFS 缓存一小时后永久失效

这是一条完整的失效链，每一环单独看都不起眼，叠起来让二级缓存只在首小时有效。

1. 首次查询写入行，`created_at` 为 `t0`，`created_by` 为用户 A。见 `nwp_forecast.py:131-149` 与 `schema.sql:297-311`。
2. 读取按 `created_at >= now() - 1h` 过滤，见 `nwp_forecast.py:116-122`。
3. 一小时后，同一键的读取不再命中。
4. 用户 A 重新拉取后 upsert，只更新 `data_json/lat/lon/days/model`，payload 里没有 `created_at`，表上也没有 `updated_at` 触发器，见 `nwp_forecast.py:140-147`。行的时间戳永远停在 `t0`，之后再也读不到。
5. 用户 B 拉取同一键后 upsert，PostgREST 走 `ON CONFLICT DO UPDATE`，命中更新策略 `created_by = auth.uid()`，B 不是 A，被 RLS 拒绝，见 `schema.sql:336-343`。异常在 `nwp_forecast.py:148-149` 被静默吞掉。
6. 删除策略只允许删 `created_at < now() - 24h` 的行，见 `schema.sql:347-350`，而全仓库没有任何地方调用删除。见 `grep` 结果只有 select 与 upsert。
7. 这一行永远留在表里占着主键，新的插入会主键冲突，更新又过不了 RLS。这个键就此永久死亡。

`schema.sql:333-334` 的注释写着“配合 cache_key 的小时桶轮换”，但 `_gfs_forecast_cache_key` 里没有小时桶，见 `nwp_forecast.py:81-87`。注释描述的设计和实现不一致，这可能是问题一直没被发现的直接原因。

修复建议按优先级排：

1. 写入收敛到一个 `SECURITY DEFINER` RPC，表上直接 revoke `insert/update`。RPC 内校验 key 与坐标、天数、模型自洽，写 `updated_at = now()`，并用 `ON CONFLICT DO UPDATE` 刷新。函数以 owner 身份运行，可以更新他人创建的行，跨用户刷新才成立。
2. 读取过滤改用 `updated_at`。
3. 增加清理。如果项目可用 `pg_cron`，用定时任务删 `updated_at < now() - 6 hours`；不可用就加一个对登录用户开放的 `prune_gfs_cache_if_due()`，每次写入时低概率触发，只删过期行，任何用户触发都无害。
4. key 里加小时桶也可以，但单独用不能解决投毒与表增长，还是需要清理。

```sql
alter table public.gfs_cache
    add column if not exists updated_at timestamptz not null default now();

create or replace function public.put_gfs_cache(
    p_key text, p_lat double precision, p_lon double precision,
    p_days integer, p_model text, p_data jsonb)
returns boolean
language plpgsql
security definer
set search_path = public
as $$
declare
    v_uid uuid := auth.uid();
begin
    if v_uid is null then
        return false;
    end if;
    -- 这里必须按 _gfs_forecast_cache_key 的同一规则重算 key 再比对，
    -- 不能信任调用方传入的 p_key。
    if p_lat is null or p_lon is null
       or p_lat < -90 or p_lat > 90 or p_lon < -180 or p_lon > 180 then
        return false;
    end if;
    if p_days is null or p_days < 1 or p_days > 16 then
        return false;
    end if;
    if p_model is null or octet_length(p_model) > 40 then
        return false;
    end if;
    if p_data is null or octet_length(p_data::text) > 100000 then
        return false;
    end if;
    insert into public.gfs_cache
        (cache_key, lat, lon, days, model, data_json, created_by, created_at, updated_at)
    values
        (p_key, p_lat, p_lon, p_days, p_model, p_data, v_uid, now(), now())
    on conflict (cache_key) do update
        set data_json = excluded.data_json,
            updated_at = now();
    return true;
end;
$$;

revoke execute on function public.put_gfs_cache(text, double precision, double precision, integer, text, jsonb) from public;
grant execute on function public.put_gfs_cache(text, double precision, double precision, integer, text, jsonb) to authenticated, service_role;
revoke insert, update on public.gfs_cache from authenticated, anon;
```

验收标准：两个不同账号先后写同一个键，第二个账号能看到第一个账号的数据被刷新；把系统时间或 `updated_at` 推到 2 小时前后，缓存命中率符合预期；`select count(*) from gfs_cache where updated_at < now() - interval '24 hours'` 长期为 0。

## S3 GFS 缓存可被投毒、可被占键

写入策略只检查 `created_by = auth.uid()` 与单行不超过 100KB，见 `schema.sql:325-331`。`cache_key` 与 `lat/lon/days/model` 是否自洽，`data_json` 是不是一份合理的逐时预报，数据库一概不校验。读策略是 `using (true)`，见 `schema.sql:318-321`，任何登录用户都能列出所有缓存行，看到别人查过哪些坐标和键。

攻击路径很直接。登录用户先读表拿到目标键，再插入一条伪造的 `data_json`。一小时内所有读该键的用户都会看到伪造预报。受害者的 upsert 又因为更新策略失败，无法覆盖。再叠上 S2 的主键占位，这个键会永久报废。

修复与 S2 是同一套。写入只走 RPC 并重算键，读取也可以改成按精确键查询的 RPC，顺便关掉整表可读。数据校验至少包括 `data_json` 是数组、长度在合理区间、每项含 `timestamp` 且在请求窗口内、温度与风速在物理量级内。

如果不想做完整校验，最小可行方案是让 key 由数据库根据参数生成，客户端不传 key。这样至少杜绝“任意键”，投毒只能发生在真实坐标上，再配合写入频率限制就有意义了。

## S4 存储配额可绕过

`save_dataset` 的配额只统计 `p_csv`，见 `schema.sql:381-399`。`datasets.name` 是 `text not null`，见 `schema.sql:15`，没有长度约束，`p_name` 只检查了非空，见 `schema.sql:378-380`。`name` 的字节数不进配额，数据集数量也没有上限。

登录用户拿到公开的 anon key 和自己的 JWT 后，可以直接调 RPC，每次传一个 10 MB 的 `name` 和 1 字节的 CSV。默认 10 MB 配额可以忽略，单用户就能把 500 MB 的免费库写满。Streamlit 界面的文件名输入不是限制，RPC 是公开可调的。

修复：

```sql
alter table public.datasets
    add constraint datasets_name_len_check
    check (char_length(name) between 1 and 200);
```

`save_dataset` 里把 `v_new_bytes` 改成 `octet_length(p_csv) + octet_length(p_name)`，并增加每用户数据集数量上限，例如 200 条。已有脏数据需要先清理再加约束，否则 `add constraint` 会失败。

验收标准：直接调 RPC 传 1 MB 的 `p_name`，必须返回拒绝；正常保存与删除仍然可用。

## S5 会话过期后静默降级

登录时只把用户信息写进 `st.session_state`，见 `auth.py:284-290` 与 `auth.py:396-412`，之后没有任何地方检查会话是否还有效。`is_authenticated()` 只看 `auth_user` 是否存在，见 `auth.py:173-176`。Supabase 的 access token 默认一小时过期，supabase-py 通常会自动刷新，但刷新失败、网络中断、服务端轮换密钥时，后续所有 RPC 都会返回 401。

`db.py` 的读写层把异常全部吞掉，返回 `False`、`0`、`[]` 或 `None`，见 `db.py:70-71`、`db.py:86-87`、`db.py:107-108`、`db.py:159-160`、`db.py:169-184`。用户看到的是“云存储 0 MB”“暂无数据集”“配额服务不可用”，不会看到“登录已过期”。这类故障最难排查，因为页面没有任何错误。

修复分两步：

1. 在数据层识别 401、`JWT expired`、`PGRST301` 这类信号，抛一个自定义的 `SessionExpired`，由页面顶层统一处理，清空会话并回到登录页。
2. 在每次 rerun 的入口用 `sb.auth.get_session()` 做一次本地检查，快过期或刷新失败时提前处理。

注意不要在 `db.py` 里直接 `st.rerun()`，数据层不应该依赖 UI 状态机。验收方式是把 Supabase Auth 的 JWT 有效期临时调到 60 秒，登录后静置两分钟再操作，页面应该回到登录页并给出明确提示。

## S6 异常被静默吞掉

`nwp_forecast.py:126-127` 与 `nwp_forecast.py:148-149` 的 `except Exception: return None` 与 `except Exception: pass` 是 S2、S3 能长期潜伏的直接原因。缓存写入被 RLS 拒绝，日志里一个字都没有。

建议给 Supabase 交互层统一加 `logging`，至少记录 RPC 名、耗时、错误类型；缓存命中与未命中计数可以放进 `st.session_state` 或一张轻量的 `app_metrics` 表，管理员面板展示最近 24 小时的命中率与错误数。Streamlit Cloud 的日志面板能看到 stdout，这比自建监控便宜。

同时保留“失败不阻断主流程”的降级策略，但要区分“可降级”和“必须报错”。缓存失败可以降级，配额函数失败已经按放行处理，见 `modules/chart_reader.py:217-224`，这个取舍可以接受，但应该在界面上留一行提示，不能完全静默。

## S7 每次 rerun 发 3 个同步 RPC

登录用户的侧边栏每次 rerun 都会同步调用 `get_storage_usage`、`get_storage_quota`、`list_datasets`，见 `app.py:493-503`。Streamlit 的每次点击、每次输入都会触发 rerun，三个 HTTP 往返叠加起来就是明显的交互延迟。Supabase 项目如果不在美区，延迟还要再加。

两种改法，建议一起做：

1. 合并成一个 `get_sidebar_state()` RPC，一次返回用量、配额、数据集列表。
2. 用 `st.cache_data(ttl=30~60, key=uid)` 缓存，保存、删除、改配额后显式清缓存。用户自己的数据按 `uid` 做缓存键，不能跨用户复用。

读图配额页的 `get_vision_quota` 也是每次 rerun 一次，见 `modules/chart_reader.py:501-502`。配额状态可以只在进入页面或 `begin_vision_call`、`record_vision_usage` 返回时更新，短 TTL 缓存即可。

## S8 缓存键精度让共享失效

`nwp_forecast.py:87` 用了 `{lat:.4f}_{lon:.4f}`，约 11 米精度。GFS 与 Open-Meteo 的网格是公里级，同城两个用户点地图几乎不可能落到同一个键上。共享缓存的目标写在 `schema.sql:290-291`，实现却把命中率压到接近零。

建议把键和请求坐标都归一到 0.01° 或 0.05°。0.05° 约 5 公里，对天气分析没有实质影响，命中率会明显上升。归一化规则要写进注释和测试，避免以后有人改回 4 位。

另外可以加一层进程内缓存 `st.cache_data(ttl=3600)`。它是 Streamlit 进程级共享，跨会话有效，能把大部分重复查询挡在 Supabase 之前，二级缓存只承担跨重启的职责。这也直接降低 S7 的 egress。

## S9 邀请码强度与生命周期

`_gen_code` 用 `secrets.token_hex(6)`，12 个十六进制字符，48 bit，见 `auth.py:635-637`。`_hash_invite_code` 是无盐 SHA-256，见 `auth.py:640-647`。`invite_codes` 没有过期时间、没有撤销标记，见 `schema.sql:83-89`。

48 bit 在库泄露后可以离线爆破，按单卡十亿次每秒估算，全空间大约八小时。拿到摘要的人未必有 service_role，但可以走公开应用的注册流程，用恢复出的明文码换一个账号。没有过期与撤销意味着一个泄露的码会一直有效到被使用。

建议改成 `secrets.token_hex(16)`，128 bit；哈希改成带服务端 pepper 的 HMAC-SHA256，pepper 放 Secrets，只存在于 Python 侧，数据库函数继续按哈希比对。再加 `expires_at`、`revoked_at` 两列，三个校验函数统一检查，管理员面板提供作废入口。迁移时旧码不匹配的问题已经在 `schema.sql:80-81` 说明了，可以顺带清理。

## S10 管理员身份双轨

`profiles.role` 定义了 `'user' | 'admin'`，见 `schema.sql:50`，但没有任何 RLS 策略或代码读取它。管理员能力来自静态 `ADMIN_PASSWORD` 加 `service_role` 客户端，见 `auth.py:465-632`。

这套做法在单人运维时够用，代价是三个。第一，所有管理查询绕过 RLS，一个代码缺陷就可能把全库暴露。第二，没有审计，谁在什么时候改了谁的配额无从追溯。第三，`role` 列让人误以为存在角色权限，实际不存在。

短期建议至少加一张 `admin_audit_log` 表，记录操作者会话、动作、目标用户、改前改后、时间，只允许 `service_role` 写。中期可以把管理员查询改成基于 `role` 的 RLS 只读策略，`service_role` 只保留创建和删除账号这两件必须走 Admin API 的事。

## S11 迁移无版本

`schema.sql` 靠手工在 SQL Editor 里重跑，见 `README.md:255-259`。`README.md:256` 还停留在“创建 datasets 表并启用 RLS”，实际脚本已经建了四张表、八组函数，文档与实现漂移。`schema.sql:353` 与 `schema.sql:426` 有两个编号为 8 的章节，属于小问题，但会让定位变难。

两种做法可选。正式一点就引入 `supabase/migrations/` 与 Supabase CLI，用 `supabase db push` 管理；轻量一点就在库里加一张 `schema_version` 表和一个只读 RPC，管理员面板显示版本号，脚本每次执行时更新。考虑到这个项目是单人部署，轻量方案足够，但要配合 S1 的自检。

## S12 Free 计划暂停与备份

`.github/workflows/keep-alive.yml:17-20` 只 ping Streamlit 应用，不触碰 Supabase。Supabase Free 计划长期无数据库活动会被暂停，具体阈值以项目当前条款为准。如果连续一周没人登录，应用还活着，数据库先睡过去，下一位用户登录会直接失败。

建议给 keep-alive 再加一步，用 anon key 请求一个会真正查库的端点，例如 `GET /rest/v1/datasets?select=id&limit=0`，或者调匿名的 `is_invite_code_valid`。不要用 service_role，anon key 本来就是公开的。备份策略需要按当前计划确认，免费计划通常没有长期保留，重要数据集建议定期 `pg_dump` 或升级计划，并做一次恢复演练。

## S13 缓存表可枚举

`gfs_cache` 的读策略是 `using (true)`，见 `schema.sql:318-321`。注释说这是为了避免匿名访客拿到坐标，但登录用户仍然可以 `select *` 拿到所有人的查询位置和 `created_by`。对于气象分析场景，查询位置本身可能敏感。

改成按精确键查询的 `SECURITY DEFINER` RPC 后，整表 select 就可以撤销。如果保留表读，至少撤销 `created_by` 的列级 select，并让客户端显式列出所需列，避免 `select("*")`，见 `nwp_forecast.py:118-122`。

## S14 管理员用户列表不分页

`_list_users` 直接调用 `list_users()`，见 `auth.py:668-678`。GoTrue 的 `/admin/users` 默认分页，通常是每页 50。用户数超过默认页大小后，管理员面板只显示第一页，无法给后面的用户调配额。

建议循环翻页直到返回数量小于页大小，并在面板显示总数。这个改动很小，可以顺手做。

## S15 缺档案行时行锁失效

`save_dataset` 与 `begin_vision_call` 都靠 `select ... for update` 锁 `profiles` 行来串行化并发，见 `schema.sql:393-396` 与 `schema.sql:534-537`。如果某个用户没有 `profiles` 行，`select into` 拿不到行，也就没有锁，两个并发请求可以同时通过配额检查。

新用户由 `handle_new_user` 触发器建行，见 `schema.sql:118-135`，正常路径没问题。风险在触发器上线前创建的老用户，或者触发器曾经失败过的账号。建议在部署脚本里补一次 `insert into profiles select id from auth.users on conflict do nothing`，并在两个函数开头也做一次幂等补行。

## S16 缺 CHECK 约束

当前 `schema.sql` 只有外键和主键，没有业务 CHECK。角色、配额非负、经纬度范围、天数范围、名称长度都只能靠应用层保证。应用层可以被绕过，因为 anon key 是公开的，RPC 可以直接调。

建议补一组约束，用 `do $$ ... exception when duplicate_object ...$$` 保证可重复执行。具体列表见 S4、S9、S2 的修复片段。

## S17 依赖未锁版本

`requirements.txt:8` 是 `supabase>=2.0.0`，README 也承认这一点，见 `README.md:46`。`auth.py`、`db.py` 大量依赖 `res.data` 的形状与 `rpc` 的返回约定，supabase-py 大版本变化会直接打断登录或配额。建议锁定到 CI 实际验证过的版本，并在 `tests/test_release_surface.py` 里加一条断言，防止有人改回范围。

## S18 目录名与包名冲突

本地实测 `import supabase` 会解析到仓库里的 `supabase/` 目录，因为该目录没有 `__init__.py`，被当成命名空间包。pip 安装的正规包优先级更高，所以线上通常不会出事。问题是工具链会误判，`importlib.metadata.version("supabase")` 直接报错，类型检查与某些脚本也会解析错。

可以考虑把目录改名，例如 `sql/` 或 `supabase_schema/`，并同步 `README`、测试与文档。这个改动会碰多处引用，收益是消除一个长期隐患，放在最后做。

## 控制台人工确认清单

以下项目无法从仓库验证，需要登录 Supabase 控制台逐项确认。

1. Authentication → Providers → Email，确认“允许新用户注册”已关闭。这是邀请码门禁的前提。
2. Authentication → Sessions，确认 JWT 有效期与刷新策略，记录当前值。
3. Authentication → Password，确认最小长度，建议至少 8 位；确认是否开启泄露密码检测。
4. Database → Policies，逐表确认 RLS 已开启，策略与 `schema.sql` 一致。
5. Database → Functions，确认八个函数的执行权限与 `schema.sql` 的 revoke/grant 一致。
6. Database → Extensions，确认是否可用 `pg_cron`。可用就上定时清理，不可用就用应用内低概率清理。
7. Settings → API，确认 anon key 与 service_role key 未出现在任何客户端可见位置，记录轮换计划。
8. Settings → Billing，记录当前计划的暂停阈值、备份保留、egress 配额。
9. SQL Editor 执行一次 S1 的自检 RPC，保存输出作为上线基线。
